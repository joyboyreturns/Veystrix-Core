# Nemotron 3.5 Lightning — architecture and product priorities

Status: **experimental; no production inference backend is available**. Qwen3.8-Flash-Next remains the working default. After real-device validation Nemotron is intended as the daily Hermes coding model and Flash-Next as the advanced model; switching is manual. No speed advantage has been measured.

The [official BF16 config](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-BF16/raw/main/config.json) specifies 52 layers in a fixed order: 23 Mamba-2, 6 attention and 23 MoE. It specifies 128 routed experts, top 6, one shared expert, hidden size 2688, 32 attention heads, 2 KV heads, head dimension 128, 64 Mamba heads, head dimension 64, 8 groups, SSM state dimension 128 and convolution kernel 4. The BF16 configuration has no MoE latent projection. The architecture supports MTP, but no MTP acceleration is implemented here. Nvidia's separate NVFP4 configuration is not equivalent to an MLX affine-4-bit checkpoint.

The installed mlx-lm 0.31.3 already provides Nemotron-H Mamba-2, attention, MoE and recurrent/KV caches. `model.py` uses it only for a tiny synthetic reference. `hybrid.py` constructs a hybrid model without resident routed-expert matrices, while `streaming_moe.py` supplies synthetic, per-expert affine-4-bit SSD-backed computation; synchronous reads and per-expert host copies are deliberate baseline limitations. This is not a real checkpoint importer, optimized inference engine, or a validated offload strategy.

A production design must hold the dense core and architecture-specific recurrent/KV state under a measured budget, stream exact expert tensors by validated index, provide bounded residency and cancellation, and fingerprint model/tokenizer/precision/execution/tokens. If the dense core cannot fit, bounded offload must be designed and measured. BF16 input and output embeddings alone require roughly 1.31 GiB for 131072 × 2688 × 2 bytes × 2; this is a mathematical lower bound, not a whole-model memory measurement. `memory.py` accounts for KV and Mamba state given explicit measured core, activation, pool and reserve budgets; it does not establish feasibility.

Flash-Next `store.py`, `expert_pool.py`, `prefetch.py`, `prefill.py`, `layer_major.py`, `prefill_ring.py`, `prefix_cache.py`, `prefix_session.py`, `memory_controller.py`, and `mtp.py` provide useful patterns, not compatible layouts by assumption. Flash-Next's historical layer-major numbers used reduced routing and do not establish full-routing correctness or speed; see `docs/flashnext/overnight-architecture-results.md`. Preserve its existing behavior and require exact six-expert routing plus shared expert for Nemotron.

For a single sequence and assuming BF16 embeddings, output head, convolution state and attention KV, plus FP32 Mamba SSM state, the estimator gives 1,409,286,144 bytes for the two untied embedding matrices, 49,082,368 bytes for Mamba states and 201,326,592 bytes for 32,768-token KV (1,659,695,104 bytes combined). This deliberately excludes every other dense projection, shared expert, transient, allocator overhead, expert pool and OS reserve: it is a partial arithmetic lower bound, not evidence that the core fits. The exact converted dtype, cache representation and device allocations must be measured.

The [BF16 weight index](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-BF16/raw/main/model.safetensors.index.json) reports 65,842,365,568 total bytes and names per-expert `up_proj`/`down_proj` tensors. Assuming all 23 × 128 × 2 routed matrices have the published 1856 × 2688 dimensions and BF16 elements, those matrices account for 58,749,616,128 bytes (54.71 GiB), leaving about 7,092,749,440 bytes (6.61 GiB) in the reported total. This remainder is an inference from metadata, not a measured dense-core footprint; it includes any MTP and other non-expert tensors reported by the index, and actual tensor dtypes, padding, loading conversions and peak allocations must be verified. Combined with application/OS memory, KV, temporary buffers and the pool, it makes a safe 16 GB allocation nontrivial. A production loader must be able to refuse or offload components; do not infer that a 16 GB device can run the model from this estimate.

The mlx-community affine-4-bit safetensors headers were inspected without loading tensor payloads. Summing shapes and dtypes from their metadata gives approximately 15.389 GiB in `switch_mlp` routed expert tensors and 1.166 GiB in the other listed tensors; no `mtp.` tensors were present in that metadata. These are file tensor bytes, not measured resident or peak memory, and exclude runtime workspaces, cache, GPU copies and OS overhead. The converted checkpoint stores each MoE's experts stacked by leading expert dimension; the prototype now computes per-expert slice offsets for this layout. Verify hashes, tensor inventory and outputs against the local shards before promotion.
