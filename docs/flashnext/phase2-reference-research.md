# Phase II reference research and n-gram prototype

Research reviewed 2026-11-10. External results are authors' reports, not Veystrix measurements.

- [moe-offload](https://github.com/Jakevin/moe-offload) (Apache-2.0) implements a native pthread pool and per-layer LRU for a GSQ-RCO Q2 repack of Qwen3.8, with trace tooling. Its C++ runner uses MLX 0.32.2 by default and exactness was demonstrated against its own Python path, on a 64 GB M4 Pro. Its [runner README](https://raw.githubusercontent.com/Jakevin/moe-offload/main/mlx-qwen38/cpp/README.md) explicitly limits total context to 2048 because sparse attention is unported, and says its scheduler is newer than the public Python loader. The [C implementation](https://raw.githubusercontent.com/Jakevin/moe-offload/main/mlx-qwen38/expert_io.c) hardcodes the Q2 layout, schedules larger tensors first and merges adjacent expert IDs using preadv; it does not propagate failed/short reads in `execute_one_task`. A Veystrix adaptation must preserve actual 4-bit layout, propagate read failures, and manage cancellation/buffer ownership, not import its implementation assumptions.
- [Vates](https://github.com/AMOS144/Vates) (Apache-2.0) targets Qwen3-Next 80B, a different model, not Qwen3.8. It groups tokens by expert with bounded superblocks and route-rank reduction, and uses a native pool, cross-layer prediction and adaptive MTP. It reports approx. 10.96 GiB MLX active, 11.51 GiB peak before OS and other application overhead; its fixed K=3 profile and quantized KV are not validated for this system. Route grouping is promising only with our state, logits and memory gates.
- [streamlx](https://github.com/srcterm/streamlx) (MIT) runs resident experts asynchronously while merging and reading missing expert spans. This suggests examining overlap of actual demand with resident work, while preserving accumulation order and protecting pool slot lifetimes. Its advertised output identity and throughput are for its supported models, not this checkpoint.
- [Palm-Infra](https://github.com/TencentYoutuResearch/Palm-Infra) (Apache-2.0 plus dependency notices) uses a converted `.mollm` format, packed W4/W8 and C++ native offload; direct checkpoint compatibility, quantization identity, and full Qwen3.8 state semantics are not established by that description. Study shared cache/workspaces without converting or replacing our checkpoint.
- [SpecMD](https://machinelearning.apple.com/research/specmd-expert-prefetching) challenges standard LRU/LFU locality assumptions and reports Least-Stale gains on OLMoE. Evaluate it against real Veystrix routes and physical reads, with split training/evaluation traces and bounded memory; a cache hit-rate simulation alone is insufficient.
- [Layered Prefill](https://proceedings.mlsys.org/paper_files/paper/2026/hash/c0f460c6d63599ea870ba9db63dc96a9-Abstract-Conference.html) schedules contiguous layer groups, targeting interference between concurrent decode and prefill. It supports investigating groups but does not predict an optimum for our single-request window schedule, safety constraints, or snapshots.
- [MLX custom Metal documentation](https://ml-explore.github.io/mlx/build/html/dev/custom_metal_kernels.html) notes `ensure_row_contiguous=True` may copy noncontiguous inputs. Disabling it is safe only when the kernel handles strides correctly; profile the actual layouts before changing any kernel.
- [MacPaw's Apple Silicon study](https://research.macpaw.com/publications/llm-optimizations-apple-silicon) reports batch-1 MoE gather improvements on its tested models, but no speculative decoding speedup in its tested workloads, and a fusion example regressed. These are candidates for measurement, not performance predictions for this SSD-bound checkpoint.
- [vLLM Metal offload](https://docs.vllm.ai/projects/vllm-metal/en/latest/moe_offload/) describes a global LRU, reserve for one expert layer and unchanged SwitchGLU math. It does not establish compatibility with Qwen3.8's entire multimodal/hybrid model and warns that speculative decoding is unsupported.

## Bounded n-gram deduplication prototype

`FLASHNEXT_NGRAM_DEDUP=1` makes direct lookup deduplicate clamped local row IDs within each shard and each invocation, reads/dequantizes unique rows, and gathers them in original order. It is disabled by default and has no persistent row cache. In the synthetic repeated-ID test 9 positions require 5 unique row reads instead of 9, including repeated, cross-shard and clamped indices. Both real synthetic safetensor quantized reads and fake row lookups match the existing output exactly in focused tests. This is an algorithmic request-count result, not a physical-SSD or end-to-end measurement: effectiveness depends on repetition in actual hashed rows and macOS caching. It may add Python/gather overhead for mostly unique IDs. A safe real-checkpoint exactness-gated paired benchmark is required before any promotion; assess physical reads and peak memory, including interactions with parallel reads.

Validation: `.venv/bin/python -m unittest models.flashnext.tests.unit.test_ngram models.flashnext.tests.unit.test_ngram_parallel` -> 4 tests passed. `.venv/bin/python -m pytest` was unavailable because pytest is not installed in the repository venv.
